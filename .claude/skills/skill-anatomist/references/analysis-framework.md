# 分析框架：7 维度评估标准

每个维度的详细评估方法和评分依据。

---

## 01 — 表层信息

提取以下字段。无法从文本直接获取的用 `[推测]` 标注。

| 字段 | 来源 | 备注 |
|------|------|------|
| 名称 | frontmatter `name` | 必有 |
| 定位 | 第一个 `#` 标题下的首句 | 一句话概括 |
| 解决的问题 | 从 description + 正文推断 | 用"用户没有这个 skill 时会怎样"来反推 |
| 目标用户 | 从 description 中的触发场景推断 | 具体到角色，非"所有人" |
| 影响力 | 无直接数据时综合评估 | 评估维度见下方 |

### 影响力评估（无下载数据时）

根据以下维度给出 1-10 分：

| 维度 | 权重 | 高分特征 |
|------|------|---------|
| 完整度 | 30% | 有 scripts + references + assets |
| 专业度 | 25% | 术语精准，无冗余说明 |
| 覆盖面 | 20% | 支持多场景 / 多框架 / 多语言 |
| 独特性 | 15% | 解决的问题市面少有替代方案 |
| 可传播性 | 10% | 易于理解和推荐给他人 |

## 02 — 结构分析

### 5 项布尔检查

**1. 明确目标（hasClearGoal）**

判断标准：读完前 10 行能否回答"这个 skill 做什么"。

- ✅ 首段或 description 直接说明用途
- ❌ 需要读完全文才知道它做什么

**2. 步骤化表达（hasStepByStep）**

判断标准：是否有编号步骤或 checklist。

- ✅ 有 `Step 1 / Step 2` 或 `- [ ]` checklist
- ⚠️ 有流程但无明确编号（部分满足）
- ❌ 纯散文式说明

**3. 输入输出定义（hasIODefinition）**

判断标准：用户是否知道"给什么、得什么"。

- ✅ 明确说明输入格式和输出格式
- ⚠️ 有隐含的 I/O 但未显式定义
- ❌ 不清楚输入输出边界

**4. 降低使用门槛（lowersBarrier）**

判断标准：新用户首次使用的摩擦力。

检查子项：
- 有无默认值或 auto 模式
- 有无 Quick Start 或 --quick 选项
- 有无前置条件检查
- 错误信息是否友好

**5. 可复制模板（hasReusableTemplate）**

判断标准：是否提供用户可以直接复制使用的模板。

- ✅ 提供代码模板、格式模板或文件结构模板
- ❌ 只有描述性指导

### 评分

```
score = (true 的数量)
最高 5，最低 0
部分满足（⚠️）计 0.5
```

## 03 — 价值密度

### 信息压缩度（1-5）

| 分值 | 特征 |
|------|------|
| 5 | 表格、矩阵、代码块密集；几乎无废话 |
| 4 | 结构紧凑，偶有展开性说明 |
| 3 | 混合型：部分紧凑部分冗余 |
| 2 | 文字为主，结构化程度低 |
| 1 | 散文式，信息密度低 |

量化参考：`有效信息行数 / 总行数`。表格行、代码行、checklist 行算有效。纯解释文字按 50% 折算。

### 3 项成本检查

**减少决策成本（reducesDecisionCost）**
- ✅ 提供推荐默认值、优先级排序、"选这个就对了"式的指导
- ❌ 给出一堆选项但不给建议

**减少试错成本（reducesTrialError）**
- ✅ 有反模式清单、常见错误、验证步骤
- ❌ 只说"正确做法"不提"常见错误"

**拿来就用（readyToUse）**
- ✅ 用户不需要额外学习即可开始使用
- ❌ 需要先理解概念再应用

### 评分

```
score = round(informationCompression * 0.4 + booleanCount * 0.6 * 5/3)
取整，范围 1-5
```

## 04 — 心理驱动

### 4 项机制检查

**解决焦虑（solvesAnxiety）**

识别方法：这个 skill 的目标用户在没有它时会有什么焦虑？

常见焦虑模式：
- "我不会做 X"（能力焦虑）
- "我做的 X 不够好"（质量焦虑）
- "X 太花时间了"（效率焦虑）
- "我不确定该不该这样做 X"（决策焦虑）

如果能明确识别焦虑类型，标记为 ✅ 并说明具体焦虑。

**制造确定性（createsCertainty）**

识别方法：使用后用户是否从"不确定"变为"确定"。

- ✅ 提供框架、清单、流程图、确定性的输出
- ❌ 提供开放性建议，用户仍需自行判断

**赋能感（empowers）**

识别方法：用户是"依赖工具"还是"因工具而成长"。

- ✅ 用户学到了新框架/思维方式，离开 skill 后仍受益
- ⚠️ 用户高效完成任务但没有成长
- ❌ 纯黑盒执行

**成就感机制（hasAchievementMechanism）**

识别方法：是否有明确的"完成"信号。

常见机制：
- 完成报告（"Done! 生成了 X 个文件"）
- 进度清单（checklist 逐项勾选）
- 质量评分（"你的代码通过了 12/15 项检查"）
- 前后对比（"优化前 → 优化后"）

### 评分

```
score = true 的数量 + (⚠️ 数量 * 0.5)
最高 5 分（4 项全 ✅ = 4，加深度分析加成最高 +1）
深度分析加成：焦虑定位极精准 +0.5，赋能与成就机制形成闭环 +0.5
```

## 05 — 可复用模式

### 提炼结构公式

方法：
1. 列出 skill 的主要组成"块"（如：参数系统、工作流、检查清单...）
2. 识别这些块之间的关系（顺序？并行？嵌套？）
3. 用 `[要素]` 格式串联为公式
4. 检查公式是否可泛化——替换领域词汇后是否仍成立

好的公式特征：
- 5-7 个要素
- 要素间有逻辑递进
- 领域无关（替换名词后仍成立）

### 匹配已知模式

从 [pattern-library.md](pattern-library.md) 中匹配。报告中列出：
- 匹配的模式名称
- 在已分析 skills 中的出现频率
- 该 skill 对此模式的实现质量（标准 / 优秀 / 创新）

## 06 — 反向构建

### 蓝图生成规则

1. 抽象出这个 skill 的"类型"（生成型 / 知识库型 / 审查型 / 哲学型 / 元技能型）
2. 按该类型的通用步骤编写蓝图（7-10 步）
3. 每步标注预计工作量（轻 / 中 / 重）
4. 标注哪些步骤可选、哪些必须

### 模板生成规则

1. 保留 skill 的骨架结构（标题层级、章节顺序）
2. 将领域特定内容替换为 `{placeholder}`
3. 保留通用写法模式（表格格式、checklist 格式等）
4. 模板必须是可以直接粘贴并填写的，不需要理解原 skill

## 07 — 改进空间

### GAP 识别方法

按以下维度逐一检查：

| 检查方向 | 问题 |
|---------|------|
| 新用户体验 | 首次使用者能否在 30 秒内开始？ |
| 信息架构 | 有无信息过载？需要几次才能消化？ |
| 容错性 | 出错时有无指引？有无 fallback？ |
| 自包含性 | 是否过度依赖外部资源？ |
| 一致性 | 术语、格式、语气是否统一？ |
| 可扩展性 | 用户能否按需定制？ |
| 示例充分性 | 关键规则有无配套示例？ |

每个 GAP 必须配一个 FIX。FIX 要具体可执行，不是"可以改进"这种废话。
