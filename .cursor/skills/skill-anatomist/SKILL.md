# Skill Anatomist

拆解 AI Skills，讲清楚它为什么好用，好在哪里，我们能学到什么。

## 输入

接受以下任一形式：
- SKILL.md 文件路径
- 技能文件夹路径（自动查找 SKILL.md + 子资源）
- 直接粘贴的技能内容

## 工作流

```
分析进度：
- [ ] Step 1: 读取与预扫描
- [ ] Step 2: 内部分析（不输出）
- [ ] Step 3: 撰写报告
- [ ] Step 4: 输出
```

### Step 1: 读取与预扫描

1. 读取 SKILL.md 完整内容
2. 如果是文件夹，扫描子结构（scripts/、references/、assets/）
3. 提取 frontmatter（name、description）
4. 统计行数、子资源情况

### Step 2: 内部分析（不输出）

这一步是内部思考过程，分析结果不直接展示给用户，而是作为 Step 3 撰写文章的素材。

用 7 个维度拆解 skill。每个维度的详细评估标准见 [analysis-framework.md](references/analysis-framework.md)。

| 维度 | 核心问题 |
|------|---------|
| 表层信息 | 这是什么？给谁用？解决什么问题？ |
| 结构设计 | 怎么组织的？为什么这样组织有效？ |
| 价值密度 | 哪些地方信息密度高？怎么做到的？ |
| 心理驱动 | 用户为什么愿意用它？击中了什么痛点？ |
| 精彩之处 | 哪些具体写法令人拍案？为什么这几句话如此关键？ |
| 可复用模式 | 能抽象出什么公式？匹配模式库中的哪些已知模式？ |
| 改进空间 | 还差在哪？怎么补？ |

同时从 [pattern-library.md](references/pattern-library.md) 匹配已知成功模式和失败模式。

### Step 3: 撰写报告

报告的形式是**一篇有洞察力的中文分析文章**，不是填表格。

#### 写作原则

1. **全部中文**。标题、正文、引用全用中文。英文仅保留 skill 原文引用和专有名词。
2. **像讲故事一样写**。引导读者从"这是什么"走到"原来如此"再到"我也能这样写"。
3. **重点讲「为什么好」**。每个分析点都要回答"这样写为什么有效"，而不只是"这样写了"。
4. **引用原文做证据**。分析到关键之处时，引用 skill 中的原句（用引用块），然后解释这句话为什么精彩。
5. **收束于行动**。读完后读者要带走至少 3 条"下次写 skill 时我可以这样做"的具体策略。

#### 文章结构

报告按以下结构组织，但每个部分之间应自然衔接，像一篇文章而非独立章节：

```markdown
# {技能名称}：{一句话概括它为什么值得研究}

> {用一句话说清这个 skill 做了什么，以及它最核心的设计巧思}

---

## 它是什么

{2-3 段。用自然语言介绍这个 skill：做什么、给谁用、解决什么问题。
不要用表格堆参数，用叙述让读者理解背景。
如果有子资源（scripts/references/assets），在这里自然提及。}

## 它的精彩之处

{这是整篇报告最重要的部分。篇幅应最长。}

{逐个拆解这个 skill 中最精彩的设计选择。每个精彩之处按这个节奏：}

{### 精彩点标题（用一个短语概括这个设计选择）}

{1. 引用 skill 原文（引用块）}
{2. 解释：这句话 / 这个设计为什么有效}
{3. 深层原因：它击中了用户的什么心理？解决了什么结构问题？}
{4. 启发：如果我们写别的 skill，这个手法可以怎么复用}

{精彩点数量：}
{- 轻量 skill（≤ 50 行）：2-3 个}
{- 标准 skill（51-200 行）：3-5 个}
{- 复杂 skill（> 200 行）：5-7 个}

## 它的结构逻辑

{分析这个 skill 的整体组织方式。不是罗列"有没有步骤""有没有模板"，
而是解释"为什么它选择了这种结构，这种结构为什么适合它要解决的问题"。}

{如果它的结构有独特之处（如：故意不用步骤、用哲学替代流程、
用矩阵替代线性流），重点分析这个选择背后的思考。}

## 它的写作模式

{提炼可复用的写作公式。}

**结构公式**

> [要素A] + [要素B] + [要素C] + ...

{解释这个公式为什么有效——不是列出来就完了，
而是说清楚每个要素承担了什么角色，要素之间是什么关系。}

**匹配的已知模式**

{从 pattern-library.md 中匹配，说明：}
{- 匹配了哪些成功模式（给出模式名和简要说明）}
{- 是否有模式的变体或创新用法}
{- 匹配了哪个模式组合类型（工作流型/知识库型/哲学型/元技能型）}

## 如果我们要写一个同类 skill

{给出一份可操作的构建指南。像在教一个同事"按这个顺序来"。}

{编号步骤，每步 1-2 句。}

{然后给出一份可直接复制粘贴的 SKILL.md 骨架模板（代码块）。
模板中的领域内容用 {placeholder} 标记，通用结构保留。}

## 它还可以更好

{诚实地指出不足，但每个不足都要配一个具体的改进建议。}

{不要用表格。用自然段落，每个不足 2-3 句：
第一句说问题，第二句说为什么这是问题，第三句说怎么改。}

## 总结：写 skill 可以从它身上学到什么

{3-5 条具体的、可操作的启发。}

{每条启发用加粗短语开头，后面跟 1-2 句解释。}

{这些启发应该是"通用的"——不只适用于这个 skill 的领域，
而是适用于任何人写任何 skill。}
```

### Step 4: 输出

将报告保存到 `技能分析/{skill-name}/REPORT.md`。

如果该目录已有 SKILL.md，直接在同目录创建 REPORT.md。
如果是分析外部路径的技能，先将 SKILL.md 复制到 `技能分析/{skill-name}/`，再生成报告。

输出完成后告知用户报告路径。

## 写作风格

- **冷静客观**。像产品研究报告，不吹不黑。
- **有观点**。不是中立到没有立场，而是有判断、有态度，但用证据支撑。
- **短句为主**。每段 3-5 句。适合扫描阅读。
- **推测标注**。没有数据支撑的判断标注 `[推测]`。

## 批量分析

如果用户提供多个 skill 路径或整个目录：
1. 逐个生成独立报告
2. 额外生成一份 `技能分析/CROSS-ANALYSIS.md` 交叉分析，内容为一篇对比文章，讲清楚哪些模式反复出现、哪些 skill 的哪些做法最值得学习
