我要做一个大胆的断言：MCP 已经奄奄一息了。我们可能还没完全意识到这一点，但迹象已经很明显。OpenClaw 不支持它。Pi 也不支持它。这并非没有理由。

当 Anthropic 发布模型上下文协议（Model Context Protocol）时，整个行业集体失智了。每家公司都争先恐后地推出 MCP 服务器，以证明自己"AI 优先"。大量资源涌入新的端点、新的传输格式、新的授权方案——所有这一切，只是为了让 LLM 能够与它们本来就能对话的服务进行对话。

我承认，我从未真正理解过它的必要性。你知道 LLM 真正擅长什么吗？自己琢磨明白。给它们一个 CLI 和一些文档，它们就能飞奔起来。

我试图避免写这篇文章很久了，但我确信 MCP 没有任何现实世界的价值，没有它我们会过得更好。让我解释一下。

## LLM 不需要特殊协议

LLM 非常擅长使用命令行工具。它们在数百万个手册页（man pages）、Stack Overflow 答案和充满 shell 脚本的 GitHub 仓库上受过训练。当我告诉 Claude 使用 `gh pr view 123` 时，它直接就能用。

MCP 承诺提供更简洁的接口，但在实践中，我发现自己还是要写同样的文档：每个工具做什么、接受什么参数，更重要的是，何时使用它。LLM 并不需要一个新协议。

## CLI 也是给人类用的

当 Claude 在 Jira 上做了意想不到的事情时，我可以运行同样的 `jira issue view` 命令，看到它看到的内容。同样的输入，同样的输出，毫无神秘感。

而在 MCP 中，工具只存在于 LLM 对话内部。出了问题，我就得去翻 JSON 传输日志，而不是自己直接运行命令。调试不应该需要协议解码器。

## 可组合性

这是差距拉大的地方。CLI 可以组合。我可以通过 `jq` 管道、用 `grep` 链接、重定向到文件。这不仅是方便；这往往是唯一可行的做法。

考虑分析一个大型 Terraform 计划：

```
terraform show -json plan.out | jq '[.resource_changes[] | select(.change.actions[0] == "no-op" | not)] | length'
```

用 MCP，你的选择要么是把整个计划倒进上下文窗口（昂贵，而且往往不可能），要么是在 MCP 服务器本身构建自定义过滤。无论哪种方式，你都在做更多工作，却得到更差的结果。CLI 方法使用的是已经存在、文档齐全、人类和智能体都能理解工具。

## 认证已经能用了

MCP 对认证这件事过于自作主张了。一个给 LLM 提供工具的协议，为什么要关心认证？

CLI 工具不在乎。`aws` 使用配置文件和 SSO。`gh` 使用 `gh auth login`。`kubectl` 使用 kubeconfig。这些都是久经沙场的认证流程，无论是我坐在键盘前还是 Claude 在驾驶，都能同样工作。认证出问题时，我按老办法修就行：`aws sso login`、`gh auth refresh`。不需要 MCP 专属的排错。

## 没有活动部件

本地 MCP 服务器是进程。它们需要启动、保持运行、不能无声无息地挂起。在 Claude Code 中，它们是作为子进程启动的，能工作直到不能工作为止。

CLI 工具只是磁盘上的二进制文件。没有后台进程，没有状态要管理，没有初始化舞蹈。你需要时它们就在，不需要时它们就隐身。

## 实际的痛点

抛开设计哲学，MCP 在日常使用中确实有摩擦：

**初始化不稳定。** 我数不清因为 MCP 服务器启动不起来而重启 Claude Code 的次数了。有时重试一下就行，有时得清除状态从头来过。

**重复认证没完没了。** 使用多个 MCP 工具？祝你好运，每个都要单独认证。而使用 SSO 或长期凭证的 CLI 就没有这个问题。认证一次就完事。

**权限是非黑即白的。** Claude Code 允许你按名称将 MCP 工具加入白名单，但仅此而已。你无法限制为只读操作，也无法限制参数。用 CLI，我可以将 `gh pr view` 加入白名单，但 `gh pr merge` 需要审批。这种细粒度很重要。

## 那什么时候 MCP 才有意义？

我不是说 MCP 完全没用。如果一个工具真的没有对应的 CLI，MCP 可能是正确的选择。我在日常工作中仍然会大量使用，当它是唯一可用的选项时。

我甚至可以争辩说，标准化接口有其价值，而且可能有些用例比 CLI 更合适。

但对于绝大多数工作，CLI 更简单、调试更快、更可靠。

## 真正的教训

最好的工具是那些既适合人类又适合机器的工具。CLI 已经有了几十年的设计迭代。它们可组合、可调试，并且搭借了已经存在的认证系统。

MCP 试图构建一个更好的抽象。结果发现我们已经有了一个相当不错的抽象。

## 给构建者的恳请

如果你是一家正在投资 MCP 服务器但没有官方 CLI 的公司，停下来重新思考你在做什么。先发布一个好的 API，然后发布一个好的 CLI。智能体会自己搞明白的。
