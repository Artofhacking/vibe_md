# MCP 已死，CLI 当立

> **原文**：MCP 已死，CLI 当立
> **转化日期**：2026-03-05

---

## 概览

MCP 可能是 AI 工具领域最经典的一次"集体跟风"——所有人都在为一个 LLM 本来就不需要的问题构建解决方案。这篇文章从五个维度拆解了为什么 CLI 才是 LLM 工具调用的正道，以及为什么"给人类设计的工具"天然就是给 AI 最好的工具。如果你正在纠结要不要给自己的产品接 MCP，先花五分钟读完这篇再说。

---

## 正文

### 一场集体失智

Anthropic 发布 MCP（Model Context Protocol，模型上下文协议）的时候，整个行业的反应就像看到邻居装了新款智能门锁——不管自己家门结不结实，先买一个再说。每家公司都争先恐后地推出 MCP 服务器，新端点（Endpoint）、新传输格式、新授权方案，资源哗哗往里砸。

结果呢？所有这一切，只是为了让 LLM 能够与它们**本来就能对话**的服务进行对话。

这个模式在技术史上反复出现：一项新技术火了，行业的第一反应不是"我们需要它吗？"，而是"别人都上了，我们不能落后"。CORBA 是这样，SOAP 是这样，微服务是这样，现在轮到 MCP 了。OpenClaw 不支持它，Pi 也不支持它——这不是巧合，这是信号。

### 给鱼装自行车

LLM 擅长什么？自己琢磨明白。

这不是夸张。想想它们的训练数据里有什么：数百万个 man pages、Stack Overflow 上所有那些 "how do I grep recursively" 的回答、GitHub 上无穷无尽的 shell 脚本。CLI 是 LLM 的母语，就像水是鱼的母语一样。你告诉 Claude 去跑 `gh pr view 123`，它不需要查手册、不需要特殊接口，直接就能干活。

MCP 承诺的是"更简洁的接口"。但实践中你发现，该写的文档一点没少——每个工具做什么、接受什么参数、什么时候该用它。这些工作在 CLI 方案里一模一样要做。MCP 唯一减少的是你理解"为什么不需要 MCP"的时间。

给 LLM 发明一套专属协议来调用工具，就像给鱼装自行车——技术上是可以做到的，但鱼在水里本来就游得挺好。

### 调试不应该需要考古学学位

这是我最喜欢的一个论点，因为它太实际了。

当 Claude 在 Jira 上做了什么意想不到的操作，你怎么排查？如果用 CLI 方案，简单得令人感动——跑同样的 `jira issue view` 命令，看到它看到的内容。同样的输入，同样的输出，零神秘感。

而在 MCP 的世界里，工具调用只存在于 LLM 对话内部。出了问题你得翻 JSON 传输日志，像考古学家刷土一样小心翼翼。这不叫调试，这叫考古。

背后有一条更深的设计哲学：**最好的开发者工具链，人和自动化用的是同一套接口。** Docker CLI 是这样，Git 是这样，kubectl 是这样。它们之所以好用，很大程度上是因为你可以先手动跑一遍确认效果，再放心交给自动化。MCP 打破了这个惯例，在人类和 AI 之间硬插了一层——仿佛我们的调试能力还不够差似的。

### 管道哲学 vs 封闭接口

这是差距从"不太方便"拉到"根本不可行"的地方。

CLI 天然支持 Unix 哲学（Unix Philosophy）的管道组合。`jq` 过滤、`grep` 筛选、管道串联、重定向到文件——不只是方便，很多时候是**唯一可行的做法**。比如分析一个大型 Terraform 计划：

```bash
terraform show -json plan.out | jq '[.resource_changes[] | select(.change.actions[0] == "no-op" | not)] | length'
```

一条管道，精准定位。换成 MCP？两条路都是死胡同：要么把整个计划塞进上下文窗口（Context Window）——昂贵且经常撞 token 天花板；要么在 MCP 服务器里为这个特定需求写自定义过滤——恭喜，你刚为一个本该一行管道解决的问题写了一个后端接口。

这暴露了一个结构性缺陷：**MCP 是封闭的，CLI 是开放的。** 管道组合让你用现有工具的排列组合解决新问题，不需要等谁给你写接口。MCP 的能力天花板，由服务器作者的想象力决定。

如果把这个对比放到文明尺度来看——Unix 管道哲学之所以活了五十年还在壮大，是因为它解决了一个永恒的问题：怎么用有限的组件应对无限的需求。而 MCP 的封闭模型，本质上是在开历史的倒车。

### 认证：别重新发明轮子

MCP 对认证这件事过于自作主张了。一个给 LLM 提供工具的协议，为什么要关心用户怎么登录？

CLI 工具的认证方式久经沙场：`aws` 用配置文件和 SSO，`gh` 用 `gh auth login`，`kubectl` 用 kubeconfig。无论是人坐在键盘前还是 Claude 在驾驶，一视同仁。出了问题？`aws sso login`、`gh auth refresh`——老办法，不需要查阅任何 MCP 专属的排错指南。

这里有一条更广泛的工程智慧：**不要为新系统发明新的认证方案，除非你有极其充分的理由。** 认证是安全领域中最容易出错、最难调试的部分。每多一种认证流程，就多一个攻击面，多一个要维护的代码路径。CLI 方案的优雅在于"搭便车"——站在几十年认证工程的肩膀上，而不是从零开始。重新造认证的轮子，是那种看起来很有技术含量、实际上最容易翻车的事。

### 最好的组件是不存在的组件

本地 MCP 服务器是进程——需要启动、保持运行、不能无声无息地挂掉。在 Claude Code 里，它们作为子进程启动。"能工作直到不能工作为止"——运维老兵听到这句话大概会条件反射地摸鼠标准备写事故报告。

CLI 工具是磁盘上的二进制文件。没有后台进程，没有状态，没有初始化仪式。需要时即在，不需要时隐身。无状态（Stateless）的威力就在这里：出了问题重新跑一次，不用操心"上次是不是搞坏了什么内部状态"。

软件工程有个反直觉的真理：**最可靠的组件是不存在的组件。** 你删不掉的代码不会出 bug，你不启动的进程不会挂。MCP 在你的系统里多加了一个活动部件，而 CLI 方案的活动部件数量是零。

### 从纸面到体感的痛

理论归理论，实际用起来 MCP 的摩擦也是真实的：

**初始化不稳定。** 因为 MCP 服务器启动不起来而重启 Claude Code——这种事发生的频率已经多到不值得单独记录了。有时重试就好，有时得清除状态从头来过。每次都是那种"等了 30 秒发现白等了"的无奈。

**重复认证没完没了。** 多个 MCP 工具？每个都要单独认证。而 SSO 或长期凭证的 CLI，认证一次搞定全部。

**权限是非黑即白的。** Claude Code 允许按名称把 MCP 工具加入白名单（Allowlist），但粒度到此为止——你没法说"允许读但不允许写"。而 CLI 方案中，`gh pr view`（只读）自动通过，`gh pr merge`（破坏性操作）需要审批。这种细粒度权限控制（Fine-grained Permission）在生产环境中不是锦上添花，是刚需。

### 话说回来

公平地讲，MCP 不是一无是处。如果一个工具确实没有对应的 CLI，MCP 可能是目前最好的选择。标准化接口本身也有价值——至少它让不同 LLM 可以用同一种方式调用工具，免得每家各搞一套。

但关键词是"绝大多数"：对于绝大多数工作，CLI 更简单、调试更快、更可靠。MCP 的合理定位是补充，不是替代——更不是"AI 优先"的通行证。

### 一条简单的优先级

MCP 试图构建一个更好的抽象（Abstraction）。结果发现我们已经有了一个相当不错的抽象——它叫 CLI，已经迭代了五十年。

最好的工具既适合人类又适合机器。在已有方案足够好的地方发明新方案，往往不是创新，而是过度工程（Over-engineering）。不是每个问题都需要"协议级"的解决方案。

如果你是一家正在投资 MCP 服务器但还没有官方 CLI 的公司——**停下来**。先发布一个好的 API，再发布一个好的 CLI。智能体会自己搞明白的。

能让人用好的东西，AI 用起来只会更顺手。这或许是整个 AI 工具领域最被低估的一条真理。

## 要点提炼

1. **LLM 天然擅长 CLI**。训练数据中的 man pages、shell 脚本、Stack Overflow 答案让 CLI 成为 LLM 的母语，额外协议是多此一举。

2. **调试透明性是杀手锏**。人和 AI 用同一个接口，出问题直接复现，不用翻 JSON 日志搞逆向工程。

3. **可组合性决定能力天花板**。CLI 管道组合用现有工具解决新问题，MCP 封闭接口把你锁在工具作者的想象力范围内。

4. **不要为新系统发明新认证**。搭便车用已有认证基础设施，比从零构建更安全、更可靠、更容易调试。

5. **最可靠的组件是不存在的组件**。CLI 是无状态的二进制文件，MCP 是需要管理生命周期的进程。少一个活动部件就少一类故障。

6. **MCP 的合理定位是补充**。没有 CLI 替代品时它有价值，但对于绝大多数场景，先把 CLI 做好才是正道。

## 术语表

| 术语 | 英文 | 释义 |
|------|------|------|
| 模型上下文协议 | MCP (Model Context Protocol) | Anthropic 提出的标准化协议，让 LLM 通过统一接口调用外部工具和服务 |
| 上下文窗口 | Context Window | LLM 单次对话能处理的最大 token 数量 |
| 细粒度权限控制 | Fine-grained Permission | 对不同操作设置不同级别的访问权限，而非简单的全有或全无 |
| Unix 哲学 | Unix Philosophy | "做好一件事"的设计原则，每个工具专注单一功能，通过管道组合实现复杂任务 |
| 过度工程 | Over-engineering | 为简单问题构建过于复杂的解决方案 |
