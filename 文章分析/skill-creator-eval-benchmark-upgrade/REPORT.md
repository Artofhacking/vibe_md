## 概览

这是 Agent Skills 发展史上一个里程碑式的更新。Anthropic 把软件工程中最核心的三件事——测试、基准测试、迭代优化——搬进了 skill-creator，而且全程不需要用户写一行代码。听起来像是在说"我们给你的 Word 文档装了个 CI/CD 流水线"，但它确实做到了。如果你正在用 Agent Skills（或者打算用），这篇值得仔细看——它解决的是 Skills 从"感觉能用"到"确定能用"的信任鸿沟。

## 正文

### 一个尴尬的现实：Skills 一直在"裸奔"

自去年 10 月 Agent Skills 发布以来，大量用户开始创建自己的技能。但这些用户有一个共同特征——他们大多是领域专家，不是工程师。他们精通自己的工作流程，知道"好的输出长什么样"，但完全没有工具去回答三个关键问题：

- 换了新模型，这个 Skill 还好使吗？
- 它是不是只在该触发的时候才触发？
- 改了一版，到底是变好了还是变烂了？

没有测试，Skills 就像一段从来不跑单元测试的代码——它可能工作得很好，但你心里永远悬着一根弦。用软件工程的术语说：这是在生产环境里 YOLO。

这次更新的本质，是把软件开发里最成熟的实践——测试、基准、迭代——移植到了 Skill 创作领域。而且巧妙的是，它完全保留了 Skills 的"零代码"哲学：你不需要学 pytest，不需要写 assertion，只需要用自然语言描述"好的输出应该长什么样"。

### 先搞清楚：你的 Skill 属于哪一类？

在讨论测试之前，有必要厘清 Skills 的两种本质类型，因为它们需要测试的原因截然不同。

**第一类：能力提升型（Capability Uplift）**

模型原本"做不到"或"做不稳定"的事，通过 Skill 注入特定技巧和模式来稳定输出。Anthropic 官方的文档创建类 Skills 就是典型例子——它们编码了仅靠提示词难以稳定获得的技术和模式。

这类 Skill 有一个独特的宿命：随着模型能力的进化，它们可能会变得不再必要。想象一下，早期你需要一个 Skill 教 Claude 怎么正确处理 PDF 表单，但如果 Claude 的下一个版本原生就学会了这件事，那这个 Skill 就该"光荣退休"了。

**第二类：偏好编码型（Encoded Preference）**

模型每一步都能做，但需要按照你团队的特定流程严格排序。比如按固定标准审查 NDA 合同、按公司模板生成周报、用特定格式提交代码审查。

这类 Skill 更加持久——只要你的流程不变，它就一直有价值。但它的风险点不同：模型可能会"自作主张"偏离你精心设计的流程，做出看起来不错但实际上跳过了关键步骤的输出。

这个分类之所以重要，是因为它直接决定了你的测试策略：

- 能力提升型 → 监控模型通用能力是否已追上或超越 Skill，一旦基线模型无需 Skill 即可通过测试，该 Skill 即可退休
- 偏好编码型 → 验证 Skill 是否忠实还原真实工作流，而非模型的"自由发挥"

无论哪种，测试的目的都是把一个"看起来管用"的 Skill 变成一个"确切知道管用"的 Skill。

### Evals：给 Skills 装上单元测试

这是整次更新中最重要的功能，没有之一。

用法极简：你提供测试提示词（test prompt），再描述"好的输出应该是什么样"，skill-creator 自动运行 Skill 并判断是否达标。如果你写过软件测试，这个流程会非常亲切——只不过你的 assertion 是用自然语言写的，而不是 `assertEqual`。

来看一个真实案例。Anthropic 的 PDF Skill 曾经无法处理一种特殊场景："非填表表单"——就是那种没有预定义字段的 PDF，你必须在精确坐标上放置文字。这种失败靠人工抽检可能好几周都发现不了，但 evals 精准定位了失败场景。团队据此修复为"锚定已提取文字坐标"的策略，问题彻底解决。

Evals 带来两个至关重要的实际价值：

**第一，及早发现质量回归。** 模型更新、基础设施变动、依赖链改变——任何一环的变化都可能导致原本工作良好的 Skill 突然失效。定期跑 evals 就像给你的 Skill 装了一个心电监护仪，异常心跳一出现就能收到警报，而不是等到患者（你的用户）已经倒下。

**第二，判断能力提升型 Skill 是否已经"过时"。** 这是一个很有意思的视角：如果基线模型在不加载 Skill 的情况下就能通过所有 evals，这说明 Skill 编码的技巧可能已经被模型内化了——这个 Skill 并没有坏，它只是不再被需要了。这种"光荣退役"的判断，在没有 evals 的时候几乎是做不到的。

### Benchmark 模式：标准化的性能仪表盘

如果说单次 eval 是"这次手术成功了吗"，那 Benchmark 模式就是"这个医生的整体手术成功率是多少"。

它支持批量运行同一组 evals，输出三个核心指标：

- **通过率**（Pass Rate）—— Skill 在多大比例的测试场景中达标
- **执行时间**（Elapsed Time）—— 每次运行花了多长时间
- **Token 消耗**（Token Usage）—— 每次运行用了多少 token

这三个数字放在一起，你就有了一张可追踪的成绩单。在模型更新后跑一次，看看通过率有没有掉；在 Skill 迭代前后各跑一次，看看新版是不是真的更好了。

更妙的是，这些数据可以本地存储、接入仪表盘、甚至插入 CI/CD 系统。这意味着你可以像管理软件质量一样管理 Skill 质量——Skills 持续集成，听起来像科幻，但现在已经是现实。

### 多智能体并行 + 比较智能体：更快、更公平的测试

**多智能体并行运行**

传统的顺序执行有两个问题：慢，而且上下文会互相污染——前一个测试的残留信息可能影响后一个测试的结果。新版 skill-creator 为每个 eval 启动独立的智能体，在干净的上下文中并行运行，每个实例都有自己的 token 和时间指标。结果更快出来，还杜绝了交叉污染。

**比较智能体（Comparator Agent）**

这是我最喜欢的设计。你可以同时运行"Skill A vs Skill B"或"有 Skill vs 无 Skill"的 A/B 测试。关键在于"盲测"——一个第三方智能体在不知道哪个输出来自哪个版本的情况下进行客观打分，消除主观偏差。

这跟医学界的双盲实验是一个道理：不知道哪个是新药、哪个是安慰剂，评估才有可信度。在 AI 领域，"自己评价自己"的问题已经被吐槽了无数次，而比较智能体正是对这个问题的一个优雅回应。

### 触发描述智能调优

随着 Skill 库越来越大，一个隐蔽但致命的问题浮出水面：触发准确性。

Skill 的描述就像是它的"门牌号"——描述太宽泛，路过的人都会误闯进来（假阳性）；描述太窄，真正需要它的人根本找不到（假阴性）。当你只有三五个 Skills 时这不是问题，但当 Skill 库膨胀到几十上百个时，精确触发就成了生死攸关的事。

Skill-creator 现在可以分析当前描述与历史样本提示之间的匹配度，然后建议优化文字，同时降低假阳性和假阴性。实际效果：在 Anthropic 自己的 6 个公开文档创建 Skills 上测试，5 个的触发准确率显著提升。

这让我想起搜索引擎优化（SEO）的逻辑——你写的不是给人看的描述，而是给模型"理解并匹配"的描述。两者的核心挑战都一样：如何用最少的文字传达最精确的语义边界。

### 未来方向：从"怎么做"到"做什么"

这一段是整篇文章中最让人兴奋的前瞻。

今天的 SKILL.md 本质上是一份"实现计划"（How）——它详细告诉 Claude 如何做某件事，步骤 1、步骤 2、步骤 3，事无巨细。但如果模型变得足够聪明，也许未来你只需要描述"目标"（What）——"我要的输出长这样，满足这些约束就行"——模型自己推导实现路径。

这个演进方向，和编程语言的发展史如出一辙。从汇编语言的"把这个值放到这个寄存器"，到 SQL 的"给我满足这个条件的数据"——每一代抽象都在从 How 走向 What。Skills 体系正在走同一条路。

而本次发布的 evals 框架，恰恰是迈向这个未来的关键一步——因为 evals 本身就是在描述"What should happen"。当 evals 足够全面、足够精确时，它们就是 Skill 本身的最佳表达。到那一天，"Skill = 一组 evals + 一句目标描述"就够了，模型负责填充中间的所有 How。

## 要点提炼

1. **Skills 有两种本质类型，测试策略不同。** 能力提升型需要监控"是否过时"，偏好编码型需要验证"是否忠实"。搞清楚你的 Skill 属于哪一类，决定了你应该怎么测。

2. **Evals 是整次更新的核心。** 用自然语言定义"好的输出长什么样"，skill-creator 自动执行并判断。PDF Skill 的真实案例证明，evals 能精准定位人工抽检根本发现不了的失败场景。

3. **Benchmark 模式让 Skill 质量可追踪。** 通过率、执行时间、Token 消耗三个指标组成的成绩单，支持接入 CI/CD 系统，实现 Skills 持续集成。

4. **比较智能体解决了"自评不可信"的老问题。** 盲测 + 第三方评判的设计，和医学双盲实验一个道理，让 A/B 对比终于有了可信度。

5. **触发描述调优是 Skill 库规模化的关键。** 描述太宽会误触发，太窄会漏触发——这和 SEO 面临的挑战本质相同。

6. **未来方向：Skill 从"How"走向"What"。** 当 evals 足够精确时，它们就是 Skill 本身——Skill = 一组 evals + 一句目标描述，模型负责填充所有实现细节。

## 术语表

| 术语 | 英文 | 释义 |
|------|------|------|
| 能力提升型技能 | Capability Uplift Skill | 弥补模型原生能力不足的技能，随模型进化可能被淘汰 |
| 偏好编码型技能 | Encoded Preference Skill | 编码团队特定工作流程的技能，价值取决于流程保真度 |
| 评估测试 | Evals | 用自然语言定义的自动化测试，检验 Skill 输出是否达标 |
| 基准测试 | Benchmark | 批量运行 evals 并输出标准化性能指标 |
| 比较智能体 | Comparator Agent | 以盲测方式对比两个版本输出的第三方评判智能体 |
| 触发描述 | Trigger Description | Skill 的描述文字，决定何时被自动匹配和触发 |
