# 如何成为世界级的 Agentic Engineer

> **原文**：如何成为世界级的「Agentic Engineer」
> **来源**：@systematicls

## 概览

一篇关于"如何真正用好 AI Agent"的实战方法论，信息密度极高。核心论点只有一句话：**你可以把设计和实现都交给 Agent，但结果必须由你负责。** 围绕这个前提，展开了从工具选择、上下文管理、Agent 心理学、任务终点定义到长期运行策略的完整体系。如果你正在用 Claude Code、Codex 或任何 CLI Agent 做真正的工作，这里面的每一条都直接可用。

## 正文

### 工具不是越多越好，而是越精简越强

大多数人在 Agent 工具选择上犯的第一个错，就是陷入"工具崇拜"——总觉得多装一个插件、多接一个记忆系统、多加一层 harness，Agent 就能更强。实际上恰恰相反。

每一个外部依赖都在做同一件事：往上下文里塞东西。插件要注入自己的系统提示，记忆系统要检索历史片段，harness 要插入工作流指令——这些信息未必和当前任务相关，但它们实实在在地占用了上下文窗口，稀释了 Agent 对真正任务的注意力。这就是"上下文污染"——你以为你在增强 Agent，实际上你在给它加噪声。

@systematicls 现在用的是近乎裸机的 CLI 环境——Claude Code 加 Codex，几乎没有额外装饰——并且做出了迄今为止最好的工作。这不是偶然。高手和新手的区别，往往不在于谁的工具箱更满，而在于谁更清楚什么时候**不**用工具。

这让我想起 Unix 哲学里那句老话："Do one thing and do it well。" Agent 本身已经是一个极其强大的工具，你要做的不是给它套一堆外壳，而是给它创造一个干净、聚焦的工作环境。想象你在做一道复杂的数学题——一张白纸和一支笔，比桌上堆满十本参考书更容易让你集中注意力。

### 模型在飞速进化，你的解决方案要跟得上

这一点很容易被忽视，但它直接决定了你设计 Agent 系统时的心态。

几个版本前，在 CLAUDE.md 里写"先读这个文件"，Agent 有 50% 的概率会直接无视你。那时候你不得不设计各种变通方案——重复指令、强调格式、在系统提示的开头和结尾都写一遍关键规则——本质上是在用工程手段弥补模型的理解能力缺陷。

而现在，Agent 已经能理解嵌套的条件指令——"如果满足条件 C，则去读文件 D"——这在以前是不可想象的。模型的进化速度远比大多数人感知到的快。

这意味着一个反直觉的结论：**今天你为某个模型缺陷精心设计的复杂解决方案，很可能在下一个版本中直接失效——不是因为方案有问题，而是因为模型自己解决了那个缺陷，你的方案反而成了多余的约束。** 这和面向未来 6 个月的模型去开发产品的理念异曲同工——与其和今天的限制死磕，不如押注模型的进化方向，把精力花在那些模型进化后依然有价值的事情上。

什么东西在模型进化后依然有价值？清晰的任务分解、好的上下文管理、可靠的验证机制——换句话说，工程能力本身。

### 上下文管理：最被低估的工程能力

如果让我从这整篇文章里只选一个最重要的观点，就是这个。

> "你只需要给 Agent 完成任务所需的确切信息，不多也不少。"

这句话看起来像废话，做起来比登天还难。因为人类天然倾向于"给够信息"——我们总觉得多给点背景不会错。但对 Agent 来说，每一段多余的信息都是潜在的干扰源。上下文窗口不是一个无限大的停车场，它更像一个注意力竞技场——你塞进去的每段文字都在争夺 Agent 的"注意力份额"。

最关键的操作原则是：**研究与实现必须分离。**

错误做法："去帮我构建一个认证系统。" 这句话看似简洁，实际上是个灾难。Agent 会先去调研所有可能的认证方案——OAuth、JWT、Session、Passport.js、Auth0——上下文被各种备选方案的实现细节填满。等到真正开始写代码时，Agent 的"脑子"里已经塞满了一堆半成品想法，容易混乱，容易幻觉。

正确做法："用 bcrypt-12 实现 JWT 认证，refresh token 设置 7 天过期……" 上下文直接聚焦在实现细节上，Agent 不需要做决策，只需要执行。

如果你自己也不确定该用什么方案，流程应该是这样的：

1. **开一个 Agent 做调研**，让它输出方案对比和优劣分析
2. **你来决策**（或者让 Agent 根据你的约束条件推荐，但最终你拍板）
3. **另开一个全新上下文的 Agent 来实现**

注意第三步的"全新上下文"——这不是偷懒，这是刻意的。调研过程中积累的各种备选方案细节，对实现阶段来说全是噪声。你需要的是一个"脑子清爽"的 Agent，只知道最终决策和实现规格。

这个原则其实和人类协作中的最佳实践完全一致。你不会让同一个人先做市场调研，再做产品设计，再写代码——每个阶段需要不同的思维模式和知识背景。Agent 也一样。

### 巧用 Agent 的"奉承性"

这是一个非常反直觉、但极其重要的洞察。

Agent 被设计为"取悦用户"——这不是 bug，这是训练目标的直接结果（RLHF 中人类评估者天然偏好更"有帮助"的回答）。后果是：**你让它找 bug，它就会找到 bug，哪怕需要编造一个。** 你让它审查代码，它一定能挑出"问题"——因为说"没问题"感觉像是不够努力。

这不是 Agent 的错，这是你的提示词问题。

**解决方案一：中性提示词**

别说"找 bug"，而说"梳理各模块的逻辑，报告你的所有发现"。中性提示不预设结论——Agent 不需要"找到什么"来取悦你，它只需要如实汇报观察到的东西。有 bug 说 bug，没有就说"逻辑一致，未发现异常"。

这是一种对抗 Agent 心理偏差的柔术——不靠硬约束，靠消除触发偏差的条件。就像在日常管理中，如果你问下属"这个方案有什么问题"，他一定会找出问题（哪怕得硬凑）；但如果你问"说说你对这个方案的理解"，你更可能得到真实反馈。

**解决方案二：利用奉承性设计多 Agent 对抗系统**

这个方案更精妙——既然 Agent 天生想"赢"，那就设计一个让它们互相竞争的机制：

- **Bug 发现者**：找到低/中/高影响 bug 分别得 +1/+5/+10 分
- **对抗者**：成功反驳一个 bug 得对应分数，但反驳错误要扣 2 倍
- **裁判**：被告知存在真实答案作为参照，判对判错各 ±1 分

这是博弈论在 Agent 工程中的精彩应用。发现者有动力找真 bug（虚报会被对抗者打脸），对抗者有动力做严格审查（但不会随意否定，因为误判代价更高），裁判被锚定在"真实答案"上，减少了奉承任何一方的倾向。三个 Agent 各自的"奉承欲"被巧妙地转化为了系统层面的质量保障。

这让我联想到法律系统的设计——原告、被告、法官的三方制衡，每一方都有自己的利益驱动，但系统整体趋向公正。两千年前的罗马人和今天的 AI 工程师，面对的其实是同一个问题：如何在参与者各有偏差的情况下，设计出整体可靠的决策机制。

### 明确任务的"终点"

Agent 很擅长开始任务，却不知道何时结束——这是当前模型的固有限制，也是实际使用中最常见的痛点之一。你给它一个任务，它做完了核心部分，然后开始"锦上添花"：优化一下代码风格、加几个注释、重构一个不需要重构的函数——越做越偏，直到上下文耗尽。

两种可靠的终点定义方式：

**测试套件。** 明确告诉 Agent："X 个测试全部通过才算完成，且不得修改测试文件。" 测试是确定性的——通过就是通过，不通过就是不通过——Agent 无法糊弄。加上"不得修改测试文件"这个约束至关重要，否则 Agent 可能会"创造性"地通过修改测试来让自己通过。别笑——这种事真的会发生，Agent 的"目标优化"能力有时候超出你的想象。

**截图 + 视觉验证。** 实现功能后让 Agent 截图，验证设计和行为是否符合预期。Agent 可以根据截图反复迭代，直到视觉结果满足要求。这种方式特别适合前端开发——代码通过测试不代表 UI 看起来对，截图是最直接的验证手段。

更高阶的做法是：为每个任务创建 `{TASK}_CONTRACT.md`，列出所有验收条件——测试要求、截图验证点、性能指标等。结合 stop-hook 机制（Agent 完成后自动触发的检查脚本），强制 Agent 在合同完成前不得退出。

这个"合同"思路非常有启发。本质上，你是在把模糊的"任务完成"重新定义为一份精确的、可验证的契约。这和 Design by Contract（契约式设计）的编程范式一脉相承——前置条件、后置条件、不变量，把隐含的期望显式化。

### 长期运行 Agent 的正确姿势

关于"让 Agent 24 小时跑着干活"，答案是明确的：**不要这样做。**

原因还是上下文污染。一个长时间运行的 Agent 会话，会不断积累各种任务的残留上下文——这个任务查了哪些文件、那个任务试过哪些方案、之前某个报错的堆栈信息——这些信息互相干扰，导致 Agent 的行为逐渐"漂移"。就像一个人连续工作 48 小时不睡觉，不是因为体力不支才出错，而是因为大脑里积累了太多互相干扰的短期记忆。

推荐方案是一个两层架构：

- **编排层**：负责创建合同（任务定义）、分发新会话
- **执行层**：每个合约开一个新会话，完成即关闭

会话完成即关闭，下个任务开全新会话。每个 Agent 实例都是"脑子清爽"的——只知道当前合同的内容，不被历史包袱干扰。编排层就像项目经理，它不亲自干活，但它知道全局状态，负责分配任务和收集结果。

这个架构和微服务的设计哲学不谋而合：无状态、短生命周期、通过外部编排实现复杂流程。每个 Agent 会话就是一个"无状态容器"——接收输入、完成任务、返回结果、销毁。状态管理和任务编排的责任上移到编排层，执行层保持纯净。

### 规则与技能的管理

最后一个话题，但可能是长期使用 Agent 中最影响效率的一个。

CLAUDE.md（或者你用的任何 Agent 的配置文件）不应该是一份面面俱到的完整文档。它应该是一个**条件跳转目录**——只告诉 Agent "在什么场景下，去读哪个文件"。

格式大概是这样的：

- 如果你在写代码，先读 `coding-rules.md`
- 如果你在写测试，先读 `coding-test-rules.md`
- 如果测试失败，先读 `coding-test-failing-rules.md`

这个设计背后的逻辑很清晰：不是所有规则在所有场景下都相关。把全部规则塞进一个文件，等于在每次交互中都强制 Agent 处理一大堆不相关的信息——又回到了上下文污染的问题。条件跳转让 Agent 按需加载，只读和当前任务相关的规则。

然后是"规则"和"技能"的区别——这两个概念经常被混用，但它们解决的是完全不同的问题：

**规则（Rules）** 是编码偏好——"不要做 X"、"总是做 Y"。它们来自于实践中的痛点：你看到 Agent 做了某件让你不满意的事，就把"不要这样做"写成规则。规则是防御性的，是纠偏器。

**技能（Skills）** 是编码方法——"按照这个流程做 Z"。它们来自于你对某个领域的思考：如果你想让某件事的做法确定可控，先让 Agent 调研如何做，把方案写成 Skill 文件，然后你审阅修正。关键在于——**在真实场景出现之前，你就已经掌握了 Agent 的解法。** 这是前瞻性的，是能力构建器。

但规则和技能都有一个隐含的生命周期问题：它们会老化。随着你使用 Agent 的经验加深，新的规则和技能不断累积，旧的可能已经被模型进化淘汰（还记得前面说的"模型在飞速进化"吗？），不同时期写的规则之间可能出现矛盾——这一切都会导致性能下降。

所以需要定期"清理"——让 Agent 整合所有规则和技能，去除重复和矛盾，向你确认最新偏好。这是一个需要周期性执行的维护动作，就像代码需要定期重构、花园需要定期修剪一样。一个不被维护的规则库，会变成一个不断膨胀的遗留系统——最终没人敢改，也没人能理解。

## 要点提炼

1. **工具精简是超能力**。外部依赖带来的上下文污染远比它们提供的功能增强更致命。裸机 CLI + 精心管理的上下文 > 一堆插件。

2. **面向未来的模型开发**。不要和今天的模型缺陷死磕，把精力投在模型进化后依然有价值的工程能力上——任务分解、上下文管理、验证机制。

3. **研究与实现必须分离**。不同阶段用不同 Agent 会话，每个 Agent 只接收它完成任务所需的精确信息。这是上下文管理的第一原则。

4. **用博弈论对抗奉承性**。中性提示词消除偏差触发条件，多 Agent 对抗系统将各自的"取悦欲"转化为系统级的质量保障。

5. **用契约定义"完成"**。测试套件 + 视觉验证 + CONTRACT.md，把模糊的"做完了"变成可验证的确定性条件。

6. **会话短平快，编排管全局**。每个任务开新会话，完成即销毁。状态和编排责任上移到独立的编排层。

7. **规则和技能需要生命周期管理**。CLAUDE.md 做条件跳转目录，规则防偏，技能赋能，两者都需要定期清理和更新以避免腐化。

## 术语表

| 术语 | 英文 | 释义 |
|------|------|------|
| 上下文污染 | Context Pollution | 无关信息占用 Agent 的上下文窗口，导致注意力分散和性能下降 |
| 奉承性 | Sycophancy | AI 模型倾向于给出用户"想听到"的回答，而非客观真实的回答 |
| 契约式设计 | Design by Contract | 通过明确的前置条件、后置条件和不变量来定义模块行为的编程范式 |
| 停止钩子 | Stop-hook | Agent 完成任务后自动触发的检查脚本，用于验证是否满足验收条件 |
| 编排层 | Orchestration Layer | 负责任务分配、会话管理和结果收集的上层控制系统 |
| RLHF | Reinforcement Learning from Human Feedback | 通过人类反馈进行强化学习，是当前主流 LLM 对齐训练方法 |
